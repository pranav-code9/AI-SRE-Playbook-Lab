# Evaluation harness (Chapter 6)

Replays incidents against the investigation agent, grades every run against
ground truth, and fails CI when results regress.

## Install and test

```bash
pip install -e ../agent
pip install -e ".[dev]"
pytest
```

## Scenarios

`scenarios/` holds twelve scenarios, generated by `src/sre_evals/variants.py`
(`sre-evals build-scenarios` regenerates them; a test fails if the committed
files drift from the generator).

Ten are variations of the checkout retry storm:

| Scenario | What it tests |
|---|---|
| `baseline` | The recorded case study |
| `release-hours-earlier` | Bad release at 06:00, symptoms at 10:05: needs the widened change search |
| `unrelated-release-too` | A second release in the window; rolling it back is forbidden |
| `red-herring-dependency` | Email has been slow all morning, unrelated |
| `no-traces` | No traces: metrics, logs and the diff only |
| `no-logs` | No logs |
| `mild-retries` | 45 ms timeout, two retries: weaker signals |
| `slow-burn` | Errors creep up over fifteen minutes |
| `manual-change` | Changed by hand: nothing to find or roll back |
| `payment-outage` | Payment really is down; a banner release three minutes earlier is a decoy |

The other two deliberately break that skeleton. Ten near-copies can only show
that the agent is good at one incident; these change the shape of the incident
rather than one detail of it.

| Scenario | What it tests |
|---|---|
| `load-not-fault` | Traffic quadruples and checkout saturates its HPA ceiling. Nothing is broken, so the correct answer names no faulty component and proposes no action |
| `two-hop-catalog` | Payment is flat; product-catalog is failing because its own release cut a database connection pool. The right rollback target is a different release |

Each has a `ground_truth` block:

| Field | Meaning |
|---|---|
| `acceptable_outcomes` | `root_cause_found`, `escalated`, or both |
| `root_cause` | `{"kind": "change", "release", "revision"}` or `{"kind": "component", "component", "keywords"}` |
| `mechanism_keywords` | Words the causal chain must contain (e.g. `retr`) |
| `key_evidence` | Tools a good investigation uses (reported, not required) |
| `acceptable_actions` / `forbidden_actions` | Tool calls the agent may, or must never, propose; `args` match as a subset |

## Running

```bash
sre-evals run --scripted                                   # free: scenarios with scripts in scripts/
sre-evals run --model <provider>:<model> --trials 3 \
    --price-in <usd/Mtok> --price-out <usd/Mtok>           # all twelve, three trials each
sre-evals run --model <provider>:<model> --no-structural-rules   # the Chapter 3 baseline, for comparison
sre-evals compare results.json baselines/scripted.json
```

`run` writes `results.json` and `report.md`: pass rate with a 95% interval,
confidently-wrong runs, per-scenario results, and the highest trust-ladder rung
whose evaluation bar (`thresholds.yaml`) the result clears. Feed the pass rate
to `sre-policy readiness --eval-pass-rate`.

## Recording a real incident

With the lab's fault running and the incident developed:

```bash
sre-evals snapshot --service checkout --symptom "checkout error rate above SLO" \
    --alert-start <ISO time> --out scenarios/lab-<date>.json
```

Fill in the `ground_truth` block from what you know you broke. The snapshot
records every signal the tools can reach over the window, so the agent can
replay it offline exactly.

## CI

`../.github/workflows/evals.yml` runs two tiers: unit tests plus the scripted
evaluation on every push (free, compared with `baselines/scripted.json`), and
the real model on all scenarios nightly, on demand, or on pull requests
labelled `run-evals`. Commit a reviewed `baselines/model.json` after the first
model run to turn on regression checks for it.
